## 네이버 지역검색 (Open API, `openapi.naver.com/v1/search/local`)

출처: <https://developers.naver.com/docs/serviceapi/search/local/local.md>

| 항목 | 원문 |
|---|---|
| 하루 한도 | "검색 API의 하루 호출 한도는 **25,000회**입니다" (검색 API 공통, 클라이언트 아이디별 합산) |
| `display` | "한 번에 표시할 검색 결과 개수(기본값: 1, **최댓값: 5**)" |
| `start` | "검색 시작 위치(기본값: 1, **최댓값: 1**)" |
| `sort` | `random`(정확도순) / `comment`(리뷰 개수순) |
| 인증 | 헤더 `X-Naver-Client-Id` · `X-Naver-Client-Secret` |

반환 필드: `title` `link` `category` `description` `telephone` `address` `roadAddress`
`mapx` `mapy`.

**풀 수집에 못 쓰는 이유 세 가지**

- **반경·좌표 파라미터가 아예 없습니다.** 파라미터는 `query` `display` `start` `sort` 뿐이라
  "사무실에서 반경 N m" 같은 질의를 표현할 수단이 없습니다. §7 의 "지도 API 반경 검색으로
  후보 수집" 은 네이버로 성립하지 않습니다.
- `display` 최대 5 + `start` 최대 1 → **한 질의당 영구히 5건**입니다. 페이지를 넘길 수 없어
  질의어를 바꿔가며 긁는 수밖에 없고, 그건 반경 기준 커버리지를 보장하지 못합니다.
- 1인 가격·단체석·영업시간 같은 건 애초에 반환하지 않습니다(§3 에서 벤더 입력으로 정한 대로).

**좌표 필드에 문서 자체의 모순이 있습니다 — 이건 호출로만 확정됩니다**

필드 설명은 `mapx`/`mapy` 가 "업체, 기관이 위치한 장소의 x 좌표(**WGS84 좌표계 기준**)" 라고
적혀 있는데, 같은 페이지의 응답 예시는 이렇습니다.

```xml
<mapx>311277</mapx>
<mapy>552097</mapy>
```

WGS84 경위도라면 서울은 `127.xx` / `37.xx` 이어야 합니다. 예시 값은 KATECH(TM128) 계열로
보입니다. 설명과 예시가 어긋나 있어 **어느 쪽이 현재 동작인지 문서로는 판정할 수 없습니다.**
지금 우리는 이 API 를 풀 수집에 쓰지 않기로 했으므로 막는 문제는 아니지만, 혹시 쓰게 되면
반드시 1회 호출로 확정해야 합니다(§10.2 발명 금지).

## 이 조사로 §6·§7 에 생기는 변경 (jhey 확인 필요)

1. **수집 소스**: §7 의 "1순위 공식 API (네이버 지역검색, 카카오 로컬)" 중 **네이버 지역검색은

3. **도보 시간 캐싱 주기**: 위 A/B/C. A 를 제안합니다.
4. **NCP Geocoding 과금 여부**: 사무실 좌표 1건에 필요한데, 대표 계정이 아니면 과금입니다.
   카카오의 "주소로 좌표 변환"(일 100,000건 무료)으로 대체하면 돈이 안 나갑니다 — §3 은
   "지오코딩 API 결과만 사용" 이라고만 했고 어느 벤더인지는 안 정했습니다. **카카오 지오코딩을
   제안합니다.**
5. **반경 검색 값**(§6 ⚠️ 잠정): 카카오 `radius` 최대 20,000m 안에서 정하면 됩니다. 도보 10분
   상한을 감쌀 값이어야 하고, 최종 판정은 실측 도보 시간으로 하므로 넉넉해도 됩니다. 값 자체는
   정하지 않았습니다(§10.4).

# 실측 결과 (2026-10-02, 실제 호출)

위까지는 문서 조사이고, 아래는 **발급받은 키로 실제 호출한 결과**입니다.
키 3개(카카오 REST · TMAP appKey · Google OAuth) 모두 정상 동작을 확인했습니다.

## 사무실 좌표 (§3 — 지오코딩 API 결과만 사용)

카카오 `주소로 좌표 변환` 결과입니다. 임의 입력이 아닙니다.

```
질의: 서울 서초구 사평대로53길 27-6
x = 127.021279865978   y = 37.5056429426445   (WGS84)
```

교차 검증: 이 좌표로 음식점을 거리순 검색하면 **1위가 직선 3m** 에 같은 도로명 주소
(`사평대로53길 27-6`)로 나옵니다 — 사무실 건물입니다.

## 반경별 음식점 수 (카카오 `FD6`)

| radius | `total_count` | `pageable_count` |
|---|---|---|
| 100 m | 23 | 23 |
| 150 m | 46 | 45 |
| 200 m | 91 | 45 |
| 300 m | 186 | 45 |
| 500 m | 592 | 45 |
| 600 m | 772 | 45 |
| 800 m | 1,093 | 45 |
| 1,000 m | 1,405 | 45 |

`pageable_count` 가 45 에서 멈추는 것을 페이지를 밀어 확인했습니다(radius 800, `sort=distance`).

| page | 받은 건수 | 처음 본 것 | 누적 유니크 | 거리 범위 | `is_end` |
|---|---|---|---|---|---|
| 1 | 15 | 15 | 15 | 3~68 m | false |
| 2 | 15 | 15 | 30 | 77~129 m | false |
| 3 | 15 | 15 | 45 | 129~148 m | true |
| 4 | 15 | **0** | 45 | 129~148 m | true |
| 5 | 15 | **0** | 45 | 129~148 m | true |

→ **한 질의의 절대 상한은 45건.** 1,093곳을 모으려면 타일링이 필수입니다. 반경 150 m 에서
46곳이므로 타일 반경은 그보다 작아야 하고, 수집은 1회성 + 일 10만 쿼터라 비용 문제는 없습니다.

데만 쓰고 필터 판정에 쓰지 않습니다.

## TMAP 무료 한도 안에 들어오는가 — §7 충돌이 해소됩니다

앞서 "24시간 저장 제한 때문에 매일 재계산해야 하는데 식당이 1,093곳이라 무료 1,000건을
넘는다" 고 적었는데, **그 1,093 은 반경 800 m 기준이었고 그 반경은 과하게 넓었습니다.**
위 보정으로 도보 10분이 직선 500~550 m 이므로:

| 수집 반경 | 식당 수 | 매일 재계산 | TMAP 무료 1,000/일 |
|---|---|---|---|
| 500 m | 592 | 592회 | 들어옴 (여유 408) |
| 600 m | 772 | 772회 | 들어옴 (여유 228) |
| 800 m | 1,093 | 1,093회 | **초과** |

→ **반경 600 m 이하로 수집하면 "매일 1회 재계산" 이 무료 한도 안에서 성립합니다.**
600 m 는 도보 10분 경계(직선 500~550 m)를 여유 있게 감쌉니다. 값 자체는 정하지 않았습니다(§10.4).

**주의**: TMAP 의 "일 무료제공 건수 1,000" 은 경로안내 **전체 합산**입니다(자동차·보행자·
타임머신·직선거리 계산 공통). 재계산에 772회를 쓰면 그날 남는 건 228회입니다.
