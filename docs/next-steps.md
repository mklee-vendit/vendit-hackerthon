# 작업 순서 (의존 순)

## A. DB 스키마 + RLS ← 거의 모든 것의 선행

`profiles` 외에 아무 테이블도 없습니다. §8 데이터 모델을 마이그레이션으로 내립니다.

| 테이블 | 비고 |
|---|---|
| `restaurants` | 이름·카테고리·주소·좌표·외부 출처 ID·**수집일**. 가격·수용·제약은 **저장하지 않는다**(후기 집계로 계산 — §8 단일 기준) |
| `walk_times` | 식당별 도보 초·도보 거리·측정 시각. **후기 있는 식당만** 채운다. 측정 실패는 `null` + 실패로 남긴다(직선거리 대체 금지 — §7) |
| `diet_options` | 행 추가만으로 확장 |
| `reviews` | 작성자·식당·본문·별점(1~5)·추천/비추천·**1인 가격(필수)**·단체 정보(선택) |
| `review_diet_tags` | review × option × (가능/불가) |
| `posts` `comments` `likes` | 댓글·좋아요가 **글과 후기 양쪽**에 붙는다 → 컬럼 2개 + "정확히 하나만 NOT NULL" CHECK |
| `restaurant_stats` (뷰) | 별점 평균·추천 비율·후기 수·1인 가격 집계. **뷰라서 후기를 지우면 자동 반영**(§9) |

- RLS: 전 테이블에 `public.is_member()`. 수정·삭제는 작성자 본인만 **서버에서** 강제(§10.8).
  RLS 는 컬럼을 막지 못하므로 수정 가능 범위는 컬럼 GRANT 로 좁힌다(`profiles` 와 같은 방식).
- **막는 결정**: 후기 글자 수 상한 · 단체 정보 형식 · 제약 태그가 후기끼리 엇갈릴 때 집계 규칙 ·
  삭제된 글의 댓글 처리 (§13)

## ~~B. 식당 수집 파이프라인~~ — 완료 (2026-10-02)

`bun run collect` → `supabase/data/restaurants.generated.sql` → `supabase db query -f` 로 적용.
**881곳**이 들어가 있다. 결과는 재현된다(두 번 돌려 같은 881곳·같은 요청 수 207).

- 순수 함수(타일 계획·쪼개기·중복 제거·경계)는 `src/shared/lib/collect/` 에 있고 테스트로
  박제돼 있다. 격자에 틈이 생기면 "조용히 빠진 식당"으로만 드러나므로 커버리지를
  표본으로 검사한다(`findUncoveredPoint`).
- 타일 69개(반지름 120m)로 시작해 45건에 걸린 타일 14개를 쪼개 총 125개 타일을 훑었다.
- 카카오의 단일 질의 `total_count` 는 **호출마다 움직인다**(883 → 882 관측). 650m 경계
  바로 바깥 10m 안에 식당이 29곳 몰려 있어 경계에서 1~2곳 차이는 설명이 된다. 어차피
  최종 포함 여부는 실측 도보 시간으로 판단하므로(§7) 이 차이는 결과를 바꾸지 않는다.
- 실패나 끝까지 잘린 타일이 있으면 리포트에 적고 **종료 코드 1** 로 끝낸다(§7·§10.5).

### 아래는 그때 적어 둔 설계 메모 (참고)

- 카카오 `카테고리로 장소 검색` `FD6`, **반경 650m**(확정). 사무실 좌표는 측정값
  `x=127.021279865978 y=37.5056429426445` (카카오 지오코딩 결과 — §3).
- **한 질의 상한이 45건**이라 650m 를 한 번에 못 긁는다. 작은 반경 타일을 깔아 합집합을 만든다
  (반경 150m 에 46곳이므로 타일은 그보다 작게). 일 10만 쿼터라 비용 문제는 없다.
- 순수 함수로 떼어 테스트할 것: **타일 좌표 생성 · 커버리지 검증 · 중복 제거 · 경계 판정**.
  HTTP·DB 쓰기는 경계로 밀어낸다.
- 수집일을 식당별로 남기고 실패를 숨기지 않는다(§7). 1g 목업의 "정보 수집 2026.09.28" 이 이 값이다.
- **셸에서 한글 질의를 보내지 말 것** — 깨져서 API 가 조용히 0건을 준다(실측, `api-survey.md`).

## ~~C. 도보 시간 측정~~ — 거의 완료 (2026-10-02)

`bun run measure` → `supabase/data/walk-times.generated.sql` → `db query -f` 로 적용.

**TMAP 에서 OpenStreetMap(Valhalla)으로 갈았다.** TMAP 약관의 24시간 저장 제한 때문에 매일
재측정하는 기계(pg_net 거두기·잠금·만료 뷰·Vault 키)를 들고 있었는데, OSM 은 저장 제한이
없어서 **식당 데이터가 변할 때 한 번만 재면 된다.** 그 기계 전부를 걷어냈다.

- 보행속도는 **4.6km/h** — TMAP 실측 8쌍에 맞춘 보정값이다(근거는 `api-survey.md`).
  상한 판정이 갈린 것은 32번 중 1번.
- **전 식당**을 측정한다. 후기 유무와 무관하다 — 쿼터 압박이 없어졌다.
- 실패는 행으로 남기고 직선거리로 대체하지 않는다(§7). 화면에는 도보 "—".
- 다시 돌리면 **아직 측정 안 된 식당만** 집는다. 새 식당이 생기면 그만큼만 더 잰다.
- 공개 인스턴스는 1 call/sec 공정사용이다. 정기 반복이 필요해지면 Docker 자체 호스팅으로.

# 디자인 쪽 확인이 필요한 것

- **다크 모드 전체** — 최종 시안에 다크가 없어 색상 축만 뒤집은 **파생값**이다(`index.css` 주석).
- **`--success`** — 시안에 성공 색이 없다. 토스트용 임시값이고 근거가 없다.
- **`--danger` 가 보라다** — 시안에 빨강·주황이 한 색도 없어서 그대로 맞췄다. 그래서 토큰
  이름이 뜻과 어긋난다(여기서 danger 는 "주의 안내"지 "파괴적 동작"이 아니다). 삭제 확인 같은
  데 쓸 색이 필요하면 이 토큰을 빌리지 말고 새로 받아야 한다.
