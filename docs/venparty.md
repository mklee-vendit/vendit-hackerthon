# 밥친구 (가칭) — 4·5층 점심·회식 식당 추천 + 사내 커뮤니티

> 세션 시작 시 이 파일부터 읽는다. 이 문서가 이 repo의 유일한 진입점이다.
> 상태: **v1.0 (2026-10-02)** — 요구사항 질의 완료. `⚠️ 잠정` 수치는 jhey 승인 전까지 확정값으로 쓰지 않는다.

---

## 0. 한 줄 정의
인원·예산·상황·도보거리·식사 제약을 넣으면, 벤디트 직원(벤더)들이 남긴 후기를 바탕으로 식당 목록을 보여주고 알고리즘 추천픽을 맨 위에 띄운다. 후기와 자유글로 4·5층이 소통한다.

## 1. 문제
- **현재 상황**: 4층과 5층으로 사람이 나뉘어 있어 의견 공유가 어렵다. 층마다 최애 식당이 다르고 밥도 따로 먹어서 서로의 취향을 모른다.
- **반복 비용**: 점심 메뉴, 회식·파티 메뉴를 고를 때마다 고민과 시간이 든다.
- **핵심 문제**: 인원·금액·상황에 맞는 적절한 식당을 빠르게 찾기 어렵다.

## 2. 이상적인 상태
좋은 프로덕트가 알아서 **인원수 · 상황 · 도보거리 · 벤더 후기**를 조합해 좋은 식당을 추천한다. 사람은 고르기만 한다.

## 3. 확정 사항
| 항목 | 결정 |
|---|---|
| 채널 | **웹** (모바일에서도 쓰므로 반응형) |
| 후기 주체 | **벤더 = 벤디트 직원**. 식당 방문 후 맛·서비스 전반을 글로 남긴 후기 |
| 결정 범위 | **추천만**. 식당 리스트를 보여주고 알고리즘 추천픽을 상단에 고정. 투표·확정 없음 |
| 사무실 | 서울시 서초구 사평대로 53길 27-6 (좌표는 지오코딩 API 결과만 사용, 임의 입력 금지) |
| 인원 | 고정 명단 없음. **매 검색마다 인원 입력** |
| 1인 예산 | 점심 **10,000원** / 파티 **50,000원** — **기본값이며 검색 때 수정 가능** |
| 식사 제약 | 필수. **옵션을 계속 추가할 수 있는 구조** |
| 식당 수집 | 네이버·카카오 API 연동 또는 크론 서버 크롤링 |
| 비용 | **무료 전제**. MVP 검증 후 유료화 가능. OpenAI(GPT) API는 발급 가능 |
| GPT | **MVP에서는 쓰지 않음**. 추천·이유 표시 모두 결정적 코드로 |
| 도보 상한 | 기본 **10분**, **보행자 경로 API 실측**값 사용 (API·무료 한도는 구현 전 공식 문서로 확인) |
| API에 없는 정보 | 1인 가격·단체석·식사 제약 태그는 **벤더가 후기 쓸 때 같이 입력** (1인 가격 **필수**, 단체 정보 **선택**) |
| 정보 없는 식당 | 후기 0개라 가격 등을 모르는 식당은 **리스트 하단에 "첫 후기" 유도 배지와 함께 표시**. 추천픽에는 들어가지 않음 |
| 부분 정보 식당 | 후기는 있으나 단체석·식사 제약 정보가 빈 식당은 **필터를 통과시키되 "미확인" 표시**. 추천픽에도 들어갈 수 있음(표시 유지) |
| 커뮤니티 | 필요. 음식·식당 후기 + 자유게시판 |
| 로그인 | **회사 구글 계정(@vendit.co.kr)만** |
| 후기 형태 | **짧은 글 + 별점(5점 만점, 1점 단위) + 추천/비추천** |
| 커뮤니티 기능 | **댓글, 좋아요(공감)** — 자유게시판 글과 **식당 후기 모두**에 적용. 사진 첨부 없음 |
| 글 권한 | **작성자 본인만 수정·삭제**. 관리자 권한 없음 |

## 4. 사용 시나리오
| # | 상황 | 입력 | 결과 |
|---|---|---|---|
| S1 | 평일 점심 | 인원, 도보 상한, 제약 | 1인 1만원 이하 식당 리스트 + 상단 추천픽 |
| S2 | 4·5층 합동 점심 | 인원, 도보 상한, 제약 | 같음. 층 구분 없이 벤더 후기 전체 반영 |
| S3 | 파티·회식 | 인원, 날짜, 제약 | 1인 5만원 이하 + 단체 수용 가능한 곳 |
| S4 | 다녀온 뒤 | 식당 선택 → 후기 작성 | 다음 추천에 반영 |
| S5 | 소통 | 자유게시판 글·댓글 | 층과 상관없이 의견 공유 |

## 5. MVP 범위
1. **식당 풀**: 사무실 기준 도보 반경 안 음식점을 API로 수집해 DB에 적재 (§7)
2. **검색**: 상황(점심/파티) · 인원 · 도보 상한 · 식사 제약 입력
3. **리스트 + 추천픽**: 조건 통과 식당 전체 리스트, 알고리즘 추천픽은 상단 고정
4. **벤더 후기**: 식당별 글 후기 작성·열람
5. **자유게시판**: 글·댓글·좋아요 (세부는 §9)
6. **식사 제약 관리**: 옵션 추가 화면

**MVP에서 하지 않는 것**: 투표·확정, 예약 대행, 결제, 배달 주문, 자동 알림 발송(승인 전).

## 6. 추천 로직 (초안)
```
입력: 상황(점심/파티), 인원, 1인 예산(상황별 기본값 1만/5만, 수정 가능), 최대 도보 시간(기본 10분), 식사 제약[]
1) 하드 필터 : 도보 시간 ≤ 상한
              1인 가격 ≤ 1인 예산        (후기 입력값 집계, 집계 방식 ⚠️ 잠정)
              단체 수용 ≥ 인원 (파티)    (후기 입력값 집계)
              식사 제약 위반 없음        (후기 입력 태그 집계)
              ※ 후기 0개 식당 → 필터 판정 불가 → "첫 후기를 남겨주세요" 배지와 함께 리스트 하단 별도 구역
              ※ 후기는 있으나 단체·제약 정보가 비어 있음 → 해당 조건은 통과, 카드에 "단체석 미확인"/"채식 미확인" 등 표시
                 (가격은 필수 입력이라 후기가 있으면 항상 있음)
                 미확인 식당도 추천픽 후보. 추천픽 카드에서도 미확인 표시는 그대로 유지
2) 점수      : 별점 + 추천/비추천 비율 + 최근성 (가중치·최소 후기 수 ⚠️ 잠정, jhey 결정)
3) 출력      : 통과 식당 전체 리스트, 상위 N곳(⚠️ 잠정)을 "추천픽"으로 상단 고정
              추천픽 근거는 숫자 그대로 표시 — 평균 별점, 추천 비율, 후기 수, 최근 후기 원문 1개
              (문장 생성 없음)
```
- 모든 수치(가중치·N·최근성 기간)는 `rules` 단일 파일에만 둔다. 정하기 전엔 `⚠️ 잠정` 표기.
- 필터 통과 0곳이면 조건을 몰래 완화하지 않는다. "맞는 곳 없음 + 걸린 조건"을 보여준다.
- 후기가 없는 식당은 점수·가격을 지어내지 않는다. 하단 "정보 없음" 구역에만 둔다.
- MVP는 GPT를 쓰지 않는다. 이후 도입하더라도 입력 후기에 없는 내용 생성 금지, 도입은 jhey 승인.

## 7. 데이터 수집
- **1순위: 공식 API** (네이버 지역검색, 카카오 로컬) — 식당 이름·주소·좌표·카테고리만 받는다. 무료 한도·반환 필드는 구현 전에 공식 문서로 확인하고 결과를 이 문서에 기록한다. 기억에 의존해 한도를 적지 않는다.
- **2순위: 크론 크롤링** — 가격·좌석·제약은 벤더 입력으로 받기로 했으므로 MVP에선 쓰지 않는다. 필요 시 jhey 승인 후. 캡차·프록시 우회 안 함, 속도·일일량은 코드로 상한, 차단 신호 시 중단.
- **도보 시간**: 보행자 경로 API로 사무실 → 식당 실측. 사무실이 고정이므로 **식당이 새로 들어올 때 1회만 계산해 저장**하고 검색할 때는 호출하지 않는다(무료 한도 보호). 사무실 주소가 바뀌면 전체 재계산.
- 후보 수집은 지도 API 반경 검색으로 하고, 반경 값은 ⚠️ 잠정. 최종 포함 여부는 실측 도보 시간으로만 판단한다.
- 경로 API가 실패한 식당은 직선거리로 대체하지 않는다. 도보 시간 "—"로 두고 실패 목록에 남긴다.
- 수집 실패 시 이전 데이터로 조용히 대체하지 않는다. 수집일을 식당별로 남기고 실패는 로그·화면에 드러낸다.

## 8. 데이터 모델 (초안)
- `Restaurant`: 이름, 카테고리, 주소, 좌표, 도보 시간, 외부 출처 ID, 수집일 (가격·수용·제약은 후기 집계값으로 계산, 직접 저장하지 않음 → 단일 기준)
- `DietOption`: 이름(예: 채식, 견과 알레르기 …), 추가한 사람, 생성일 — **행 추가만으로 옵션 확장**
- `ReviewDietTag`: review × dietOption × (가능/불가) — 벤더가 후기 작성 시 체크. 식당 단위 값은 후기 태그를 집계해서 만든다(입력이 없으면 "미확인", 후기끼리 엇갈릴 때 집계 규칙 ⚠️ 잠정)
- `User`: 구글 계정 ID, 이메일(@vendit.co.kr), 표시 이름
- `Review`: 작성자, 식당, 짧은 글(글자 수 상한 ⚠️ 잠정), 별점(1~5 정수), 추천/비추천, 1인 가격(필수), 단체 정보(선택 — 함께 간 인원 / 단체석 여부 중 형식 ⚠️ 잠정), 작성일
- `Post`: 자유게시판 글
- `Comment` / `Like`: 대상 = Post 또는 Review (둘 다 지원)

## 9. 커뮤니티 (요구사항만 확정, 구현 방식은 미정)
- 음식·식당 후기 + 자유게시판
- 회사 구글 계정 로그인 사용자만 읽기·쓰기 (실명 기반, 익명 없음)
- 댓글, 좋아요(공감) 있음 / 사진 첨부 없음 (텍스트 전용 → 스토리지 비용 없음)
- 댓글·좋아요는 자유게시판 글과 식당 후기 양쪽에 붙는다
- 수정·삭제는 작성자 본인만 (서버에서 작성자 ID 대조로 강제). 관리자 숨김 기능 없음
- 후기를 삭제하면 그 식당의 가격·별점·제약 집계에서 즉시 빠진다 (집계를 저장하지 않고 후기에서 계산하므로 자동 반영)
- 삭제된 글에 달린 댓글 처리(함께 삭제 / "삭제된 글입니다" 표시) ⚠️ 잠정

## 10. 작업 원칙 (Vibe_coding 공통 규칙 중 이 프로젝트 해당분)
1. **단일 기준**: 필터·점수 판정은 한 파일/한 함수에만. 화면마다 따로 계산하지 않는다.
2. **발명 금지**: 식당 정보·가격·후기·영업시간·좌표를 지어내지 않는다. 없으면 `—`. 추천 이유도 실제 후기에 있는 것만.
3. **가짜 데이터 금지**: 가짜 후기·더미 식당·테스트 게시글을 prod에 넣지 않는다. 검증용 데이터는 검증 직후 삭제까지가 한 단위.
4. **임의 임계값 금지**: 새 판정 기준은 질문으로 올리고 `⚠️ 잠정` 표기.
5. **조용한 폴백 금지**: API 실패는 실패로 보여준다.
6. **돈 나가는 일은 승인**: 유료 요금제·유료 API 전환은 jhey 사전 승인. GPT 호출도 테스트로 대량 과금하지 않는다.
7. **크롤링 절제**: 위장이 아니라 양·패턴을 코드로 묶는다.
8. **권한은 서버에서**: 글 수정·삭제 권한은 서버/DB 레벨에서 강제. 프론트 숨김은 UX일 뿐.
   @vendit.co.kr 도메인 제한도 서버에서 토큰의 이메일·도메인을 검증한다. 로그인 화면 옵션만으로 막지 않는다.
9. **완료 = 실물 확인**: 배포 후 실제 화면(데스크톱+모바일)에서 검색·추천·후기 작성이 되는 걸 보고 나서 완료 보고. 안 돌린 검증은 안 돌렸다고 쓴다.
10. **자기 코드 자기 승인 금지**: 리뷰는 Codex.
11. **시크릿**: `.env*`·API 키 커밋·문서 기재 금지. 값은 jhey가 직접 넣는다.
12. **범위 확장 금지**: 지시받은 기능만. 갈래가 생기면 묻는다.
13. **한글**: 문자열 비교는 NFC 정규화, 입력창 Enter는 `isComposing` 가드.

## 12. 기술 스택
- 웹(반응형). 별도 지정이 없어 기존 프로젝트와 같이 **Next.js + Vercel**을 기본으로 한다.
- Next.js 코드 작성 전 `node_modules/next/dist/docs`를 먼저 읽는다 ("This is NOT the Next.js you know").
- DB·인증 라이브러리는 무료 플랜 전제로 아키텍처 단계(Fable)에서 정하고 Codex 리뷰를 거친다. ⚠️ 잠정
- Vercel scope는 jhey가 지정한다. ⚠️ 미정
- Vercel 운용: sensitive env는 `vercel env pull`로 회수 불가, env를 바꾸면 반드시 redeploy, push ≠ 배포(Ready·실응답 확인 후 완료 보고).
- 시험은 prod DB가 아닌 별도 DB에서. CI·프리뷰가 prod DB를 건드리지 않게 막는다.
- MVP는 LLM 없음. 이후 도입 시 OpenAI API.
